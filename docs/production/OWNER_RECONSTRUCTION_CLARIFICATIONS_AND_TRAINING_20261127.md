## Training — engineering definition, not claims of performed training
The methodology is implemented in native executable graphs, typed representations, constrained output interfaces and learned operators. No runtime reading, retrieval, summarizing or interpreting methodology documents, no generic template creative fallback. Train from mode-native inputs and expected output structures. Preserve each Original's artistic requirements and owner-review requirement for changes.

Training workstreams:
1. Design operator supervised learning: typed concept IDs/features, visual reference encodings, native mode parameters and seed/variation inputs -> complete structured candidate design, protected attributes, spatial/visual constraints. Use reviewed design targets, diverse permitted synthetic examples and explicit failure/correction pairs. Train on field prediction, categorical/continuous attributes, structured decoding, concept alignment and candidate diversity; native code enforces hard output contracts. Compare shared backbone with specialist heads against separate modules. No requirement to use an LLM or LoRA at runtime.
2. Reference encoder and conditioning: use permitted matched source/target examples, views and role annotations. Learn identity features across viewpoints, style features across different subjects, spatial/pose features and element features. Train architecture-specific projections/control channels against the actual renderer; contrastive alignment, reconstruction and preservation losses where appropriate. Validate held-out identities/styles and unseen references.
3. Three independent image models: select pretrained compatible foundations based on actual Asterion tasks, then selectively tune weights/conditioning modules using appropriate image/condition pairs and the foundation's original training objective (noise/velocity/flow prediction as applicable). Prefer parameter-efficient training given available compute; merge compatible learned deltas into final checkpoint where supported and validated. No mandatory runtime LoRA catalogue. Evaluate text/visual conditioning, seed diversity, raw and finished quality, device inference, memory and thermal behavior separately for Anime/Cosplay/Realistic. No blind cross-architecture weight fusion.
4. Video and sound: compare pretrained video foundations first; condition on shot plan, reference assets, keyframes, motion and camera cues. If needed and feasible train temporal/identity conditioning modules using permitted sequences and consistent character views. Separate audio generation/mixing, original or authorized voice synthesis, alignment and lip-sync modules; measure continuity, motion and audio/video synchronization. Full video foundation training not a prerequisite to deliver a functioning clip engine. No voice/likeness permissions inferred from supplied reference clips.
5. Evaluation/learning: reuse explicit GradingCorpus evidence export, but the existing Gemma correction-language LoRA script is TEXT_CORRECTION_SFT_ONLY, not actual visual learning or methodology-native training. Train preference/ranking, defect detection, localized correction and validated parameter/weight updates from permitted evidence; distinguish owner grades from teacher and synthetic labels. Preserve replay data, held-out tests, hashes, candidate checkpoints, rollback and old model availability.
6. Execution: local PC data preparation, compact-model training, conversion, checkpoint management and orchestration. Use free Kaggle/Colab GPU resources when available and permitted (availability/quotas not guaranteed), with restartable checkpoints and no paid usage. No private references transferred without authorization; supplied examples are evaluation references unless appropriate training rights/permission are established. Select on measured useful improvement, not training loss or generic chatbot score. Deploy only validated models converted for the actual Android runtime.
